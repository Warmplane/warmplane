# Warmplane trust controls for existing integrations

## Summary

Deliver three opt-in controls on the v0.34.0 baseline: result sanitization across tool, resource, and prompt responses, operator-approved tool definition pinning in Control Deck, and signed ChatOps approvals with decision receipts. Ship them in that order as independently reviewable changes. Retire legacy ChatOps approval callbacks when the signed-action change ships.

## 1. Sanitize live and stored results

- Add global `policy.resultSanitization` with case-insensitive structured field names, case-sensitive regular expressions, and an explicit opaque-content exception list keyed by upstream server, content kind, and exact MIME type. Compile rules when loading config and reject invalid config before activation. An absent block preserves existing delivery behavior. Use a fixed `[REDACTED]` marker and keep `redactKeys` as the existing log redaction setting.
- Use one result sanitizer for REST, MCP stdio, MCP HTTP, and embedded delivery. Cover native and aliased tool calls, batches, resource reads, prompt messages, task results, and idempotent replay and inspection. Walk JSON values and supported MCP text blocks. Preserve protocol structure. If a configured rule matches a field essential to the envelope, withhold the result instead of returning an invalid envelope. Apply a 1 MiB post-decode inspection limit and a depth limit of 64. [MCP tool results](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) · [MCP resource contents](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Treat images, audio, binary blobs, and unknown content as opaque. An exact configured exception permits delivery of the corresponding known opaque type and records the exception in audit metadata. Withhold unknown or unlisted opaque content. Forward a stable policy error and keep raw upstream error strings out of enforcing responses, logs, and receipts.
- Sanitize before output shaping, ordinary result persistence, audit and SIEM export, and batch interpolation. Mark redacted subtrees so a batch step that references protected data fails before dispatch. Keep raw data required for drift checks or inverse registration within the existing protected operational state. Exclude it from operator result views and audit payloads.
- Stamp persisted results with the effective policy revision used at delivery. On poll, replay, or inspection, recheck access and compare policy revisions. During enforcement, withhold unstamped or mismatched results and retain their execution records. A filter failure after dispatch records the known upstream outcome separately. It must neither trigger automatic retry nor remove the idempotency claim for a completed mutation. Document the upgrade behavior and retention options for pre-existing raw records.

## 2. Pin tool definitions in Control Deck

- Add an opt-in pinning requirement per upstream server. Key approvals by server ID and raw upstream tool name so aliases and native exports share the same decision. Hash a versioned canonical representation of the upstream name, description, input and output schemas, and execution-relevant metadata before applying alias overrides. Sort object keys recursively, preserve array order, and exclude presentation-only metadata.
- Reuse supervisor discovery during mount and reconnect. For pinned servers, consume upstream tool-list change signals and refresh every 15 seconds as a fallback. Publish a complete paginated discovery result as one generation. A notification, disconnect, failed refresh, or observation age over 30 seconds makes the affected generation unavailable until discovery succeeds. Gate discovery and search before ranking, and gate dispatch again at the worker boundary using the current generation. This controls changes Warmplane has observed and bounds the age of its observations.
- Add authenticated `GET /v1/config/tool-pins` and `POST /v1/config/tool-pins/approve`. Control Deck shows missing, matching, changed, and unavailable definitions, with current and approved values rendered as escaped text. Approval submits the server, tool, and exact observed digest. Return `409` if the observed definition changed during review. Persist the reviewed definition and digest using the atomic state store, after confirmed audit authorization. Publish the pin only after persistence succeeds. Keep the capability quarantined if the write outcome is uncertain.
- Require an explicit authenticated `manageTrustControls` role permission for pin review and approval when RBAC is enabled. With RBAC disabled, require the configured daemon token for remote pin management. Apply the same administrative boundary to config mutation routes that can weaken an active trust control. Keep local file configuration under filesystem operator control.
- Bind held and approval-gated calls to the definition they were prepared against. A later revision, even one already approved for new calls, blocks the queued call and requires a new request. Apply the worker guard to forward calls, snapshot helpers, and inverses. On visibility changes, refresh the search view, catalog validators, and existing MCP notifications. Reuse signed webhooks for metadata-only quarantine notifications.

## 3. Migrate ChatOps to signed approvals

- Route approve and reject through `/v1/webhooks/actions` using distinct signed actions. Bind each token to its ticket, tenant, delegated role, expiry, immutable argument digest, and pinned definition revision when applicable. Configure the destination for one explicit tenant under RBAC. Issue cards only for that tenant and require an explicit `resolveApprovals` permission for the delegated role. Derive the principal from verified credentials or the configured delegation. Limit ChatOps decisions to the arguments the operator reviewed.
- Unify approval resolution across Control Deck, task input, and signed callbacks. Add verified ownership and explicit task linkage to tickets. Check tenant, permission, pending state, and expiry in the shared resolver. Persist one decision before releasing the waiter. A valid repeated callback returns the existing receipt without another transition. A competing decision leaves the first decision in place. Scope approval views to the tenant and return safe summaries.
- Separate callback acknowledgment, ticket decision, and upstream execution outcome. Acknowledge verified Slack callbacks with HTTP 200 within three seconds, then resolve and send feedback asynchronously. Route outbound receipts to the configured destination and record delivery success or failure against the ticket. A failed delivery leaves the decision intact. Support Teams through a documented Workflow or authenticated bot relay that submits the signed action to the same endpoint. [Slack acknowledgment contract](https://docs.slack.dev/interactivity/handling-user-interaction/) · [Teams Workflow integration](https://learn.microsoft.com/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook)
- Return `410` from `/v1/webhooks/callbacks` after upgrade and direct operators to the signed callback URL. Old cards and unscoped pending tickets require a fresh request when ownership or approval freshness cannot be established. Keep undo and cancel-send actions on their existing authorization paths. Document the Slack, Teams, and generic migration steps and surface delivery feedback in Control Deck.

## Checkpoint 1 — Result delivery and replay

1. Put rule compilation and content inspection in [`src/result_sanitization.rs`](../../src/result_sanitization.rs). Apply the same rules from REST execution, the embedded engine, and the MCP facade. Preserve the distinction between an upstream operation that failed and a completed operation whose result the policy withheld.
2. Carry the policy revision through [`src/idempotency.rs`](../../src/idempotency.rs) and [`src/tasks.rs`](../../src/tasks.rs). Verify current access before reading a stored result. Pass protected paths to the batch executor so it can reject interpolation before calling the next tool.
3. Verify the trust boundary with fixtures that put the same secret in nested tool data, prompt or resource content, and an upstream error. Check the client response, persisted result, logs, audit records, and SIEM export. Restart the daemon after a withheld mutation and verify that a retry reuses the completed execution record.

This checkpoint can ship with sanitization disabled by default. Enable it first on an integration whose result types are known. Confirm that its expected text and structured responses still work and that old results are withheld on replay. Existing records follow the operator's configured retention policy.

## Checkpoint 2 — Review and enforce tool pins

1. Attach pin discovery to [`src/supervisor.rs`](../../src/supervisor.rs). Collect all pages before publishing a generation. Use the same publication path on mount, reconnect, notification, and timed refresh. Invalidate catalog and search views when availability changes.
2. Use [`src/tool_pins.rs`](../../src/tool_pins.rs) for the observed, approved, and unavailable states. Wire the config API and [Control Deck comparison view](../../ui/src/components/tool-pins.ts) to those states. Test that a successful approval remains effective after restart and that an uncertain write still leaves the tool unavailable after reopening the store.
3. Validate the handoff from catalog to worker with two upstreams. The stdio fixture changes a definition during a hold and sends a notification. The HTTP fixture changes a definition silently and lets the fallback observe it. Check that an operator can approve the new definition for a new call and that the held call still produces zero upstream dispatches.

This checkpoint can ship with `requireToolPins` disabled by default. For a pilot upstream, configure persistent state and confirm the operator can authenticate to the pin API before enabling enforcement. Expect tools to be unavailable until the operator approves their observed definitions.

## Checkpoint 3 — Signed ChatOps cutover

1. Centralize ticket ownership, expiry, and durable decision handling in [`src/approvals.rs`](../../src/approvals.rs). Route REST approval actions, linked task input, and webhook decisions through that resolver. Record execution outcomes separately from a decision that permits execution.
2. Use [`src/approval_chatops.rs`](../../src/approval_chatops.rs) for action signing, Slack verification, and receipt delivery. Prove that verified Slack callbacks can acknowledge while decision storage is busy. Check that a Teams relay replay returns the same receipt and that a conflicting, expired, or cross-tenant action releases no waiter.
3. Verify the [operator migration procedure](../USER-GUIDE.md) against Slack, Teams, and generic callback configurations. Exercise a failing receipt destination and verify that Control Deck still shows the committed decision and its separate delivery status. Verify the existing undo and cancel-send actions along with `410` on the retired callback route.

This checkpoint changes the callback contract at upgrade. Configure `/v1/webhooks/actions` and the signing and delegation settings for each destination before cutover. Prepare operators to reissue pending requests that used old cards. Where RBAC is enabled, verify the receiving tenant and delegated role with a fresh approval before resuming routine use.

## Acceptance and release checks

| Scenario | Expected result |
| --- | --- |
| A sensitive fixture is returned as tool data, prompt text, a resource, a task result, or a cached result | The configured rule applies at every enforcing delivery path. The fixture is absent from logs, audit, and SIEM output. |
| A result contains an opaque object | Delivery succeeds only for a known type matching the exact server, kind, and MIME exception. Otherwise the result is withheld, with the upstream outcome preserved. |
| A completed mutation is retried after filtering fails or policy changes | The client receives a safe outcome and the upstream call count stays at one. A batch step cannot forward a protected value by reference. |
| A pinned definition changes during a hold, approval, reconnect, or concurrent operator review | Current discovery excludes the unverified tool, stale validators yield no `304`, and the old invocation produces zero new upstream calls. A stale approval submission receives `409`. |
| A callback is duplicated, conflicts with another decision, has expired, or belongs to another tenant | At most one authorized decision is persisted and the waiter is released at most once. Rejected callbacks cause zero dispatches. |
| The audit store, pin store, approval store, or notification destination fails | Pin and approval activation follow the committed state. Notification failure remains visible independently of the decision. |

Use fake stdio and HTTP upstreams, restart and persistence-failure fixtures, and Slack and Teams relay fixtures. Measure sanitization p50/p95 on representative text and structured payloads, pin-gate overhead against the current dispatch path, and Slack acknowledgment latency separately from resolution. Run the repository’s format, Clippy, all-target test and check, and Bun 1.4.4 bundle verification. Compare Rust changes against the branch base with Slop Gate. Update the config schema, OpenAPI spec, Warmplane skill, and affected user and integrator guides alongside the behavior changes.
